## 缺口 2：在真实项目上用 —— 已跑通，发现并修复了 5 个问题

| # | 发现 | 严重性 | 处理 |
|---|---|---|---|
| 1 | **守卫在没装 stagent 依赖的项目里静默失效**：init 写入的 `npx stagent hook pre-tool-use` 找不到命令、exit 127，Claude Code 把它当作非阻塞错误直接放行 | 严重 | hook 命令改为 stagent 自己 CLI 的绝对路径；路径不存在时 **fail closed**（exit 2 拦下操作并提示重新 init），不退回下载同名 npm 包；重新 init 会升级旧命令；服务启动时**自检** hook 真能跑、真会拒绝，不通过时结论卡第一条写明、禁止驱动 Claude Code |
| 2 | **检查永远找不到**：init 为 vitest 项目写的 `npx vitest run {path}`，vitest 的 include 不覆盖 `.stagent/runs/`，检查必然"没有测试"失败 | 严重 | init 生成 `.stagent/vitest.checks.config.mjs`（playwright 同理），checkCommand 指向它 |
| 3 | 重新 init 会**重复写入**守卫 hook（新命令不再包含旧的识别字符串） | 中 | 识别规则改为"含 `hook pre-tool-use` 且含 stagent" |
| 4 | **"N 个例子"虚高**：Claude 把 4 个例子写进同一个检查文件，它们同进同退，却显示「已验证（4 个例子）」 | 中 | 起草提示要求一例一文件、用不含函数名的大白话；服务端同一文件只登记第一条，丢弃的写明原因 |
| 5 | 给已有命令加一行输出被建成了一个**新功能**（档位判断其实只指向一个已有功能） | 低 | 档位判断只指向一个已有功能时，例子挂到它 |

其它观察（没有改）：

- 档位判断把"verify 多输出一行 projectId"判为新功能档——符合规格「改变用户可见行为就是新功能」，但意味着很多小需求都会走起草例子，花费和步骤都更多。值得在你自己用的时候感受一下是否过严。
- Claude 的实现回报里说"检查文件没被默认 vitest 配置收集，所以没运行"：它看不到怎么跑锁定检查。不影响证据（系统自己跑），但让它能自测会少一些修复轮次。
- 起草的例子文字仍然偏技术（带规则名、函数名），已在提示里要求大白话，效果要在你的项目上再看。
- 基线 11 条第一次就全部通过——基线描述的是已有行为，这是预期；但也说明基线本身证明不了检查"有力"，这正是规格只对新功能做先失败检查的原因。

## 缺口 3：你会不会认真确认例子 —— 机制已就位，数据要靠你

这一条验证的是人，不是代码；我无法替你产生数据。已经做的：

- **逐条确认**：确认例子时每条都要勾选「我读过这条例子和『检查实际在看什么』，它就是我要的行为」，全部勾选才能跑先失败检查 / 锁定。
- **锁定前可以改**：待锁定的例子可以直接改文字（写 `example.drafted { by: 'user' }`），这就是「修改率」的分子。
- **健康指标**（交付报告页顶部，只在本机，`GET /api/health`）：例子确认时的修改率、每条例子的审阅停留中位数、先失败检查不合格率与豁免率、仅 AI 声称被证伪次数、被全量回归拦下的破坏次数、无效运行、结果不稳定次数、打开抽屉 / 地图 / 计划的次数。
- **防盖章提示**：确认过 ≥ 3 条 AI 起草的例子、一条都没改、每条平均停留不到 5 秒 → 结论卡出现提示「小心确认变成盖章」（只提示，不阻止）。

建议你接下来在一个自己的真实项目上用一到两周，然后看健康指标：修改率长期是 0、停留时间只有一两秒，说明这套机制在你这里退化了，需要调整（例如强制每次至少改写一条期望，或者把摘要换成更容易对照的形式）。
